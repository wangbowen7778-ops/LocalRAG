# LocalRAG 用户手册

> 一份面向最终用户的操作指南。阅读完后，你应该能独立完成「配置 → 建库 → 上传 → 提问」全流程。

## 1. 安装

### 1.1 系统要求
- Windows 10 / Windows 11（64 位）
- ≥ 2 GB 可用磁盘空间（建议 5 GB+，用于存放向量数据）
- 网络连接（首次配置 API Key 与对话时需要）

### 1.2 安装步骤
1. 双击 `LocalRAG-Setup-x.x.x.exe`
2. 选择安装路径（建议使用默认）
3. 等待安装完成（约 10-20 秒）
4. 桌面双击「LocalRAG」图标启动

> 首次启动时，程序会在 `%APPDATA%\LocalRAG` 下创建数据目录与向量索引。**整个应用无需任何额外环境**（不依赖 Python、Node、Docker 等）。

> **v1.3.6 升级说明**（公开版，与内部里程碑号对齐）：本次随 v1.3.4（闲聊短路 + 会话等待串扰修复）、v1.3.5（检索性能优化）一并发布。`package.json` + `APP_VERSION` 从 1.3.0 升至 1.3.6。
> - **v1.3.5 检索性能优化**：分步耗时日志定位到 rerank 33 秒是主凶（deepseek-v4-flash 非流式响应慢）。rerank/plan 的 LLM 调用改用流式（`chatStream`），rerank 加 10s 超时兜底。**实测 rerank 33s→3.7s**，端到端 47s→13s。详见 [§5.9 检索性能优化（v1.3.5）](#59-检索性能优化v135)
> - **v1.3.4 闲聊短路**："你好/谢谢/在吗"等闲聊跳过检索直接主答，省 2-3 次 LLM/API 调用。首轮 cheap regex 检测，多轮 LLM 判断，失败兜底走检索（宁可不短路别漏答）。同时修复"一个会话提问时其他对话也显示等待"的串扰 bug
> - **关键认知**：流式加速 = 省掉服务端缓冲 + 避免思考链憋超时，不是省"生成时间"

> **v1.3.3 升级说明**（内部里程碑，公开版仍为 v2.0.0）：rerank 启用时直接发全文，修复 LLM 不调 read_chunk 导致截断——v1.3.2 rerank 把正确 chunk 搜到了，但 LLM 收到的是 200 字 preview（不是全文），弱模型不调 read_chunk 就答截断内容。v1.3.3 让 rerank 开时直接发 topK 全文给 LLM，不再依赖 LLM 主动调工具。详见 [§5.8 检索结果重排（v1.3.2）](#58-检索结果重排v132) 末尾 v1.3.3 增量。
> - **核心修复**：用户实测「第二章第十三条前后备案事项」——citation 列表里有完整全文（第十九-二十二条），AI 却说"被截断，暂不支持拉取"只答 (一)。根因：LLM 收到 200 字 preview + `[TRUNCATED]` 标记，本该调 read_chunk 拿全文，但弱模型不调，直接用 preview 答
> - **修复**：rerank 开时跳过 read_chunk preview 流，直接发 topK 全文——rerank 已精确挑出最相关 chunk，全文成本可接受，且不再依赖 LLM 主动调工具
> - **rerank 关时保持 read_chunk 流**——无 rerank 时 chunk 质量参差，LLM 选择性读省 token 有价值

> **v1.3.2 升级说明**（内部里程碑，公开版仍为 v2.0.0）：检索后 LLM rerank（重排候选）——召回 20 个候选片段 → Chat Provider 小 LLM 按语义相关度重排 → 取 topK 喂主答 LLM。解决「正确答案被 BM25/RRF 排到 topK 外」（长整章 chunk 关键词堆砌压过答案子 chunk，LLM 拿到错的 chunk 幻觉）。简单模式 + Agent 模式都覆盖。详见 [§5.8 检索结果重排（v1.3.2）](#58-检索结果重排v132)。
> - **核心修复**：v1.2.8/v1.2.9 调过 BM25/RRF 参数（topK 5→8、RRF_K 60→30、b 0.75→0.5）但没根治——BM25 中文 unigram 分词让条例名前缀稀释 IDF，8 个整章 chunk 分数挤在 10% 区间内，正确答案（子 chunk）被排到 rank 12、RRF 融合后 rank 6 边缘被 topK 切掉
> - **修复**：用 LLM 语义重排——LLM 看 query+chunk 联合语义，识别「第十九-二十二条备案」才是「第十三条前后备案」的真匹配，把答案从 rank 6+ 抬到前 1-2
> - **Settings +1 字段**：`enableRerank`（默认 true），UI 在「设置 → 常规」加 checkbox
> - **关键设计取舍**：① 只重排顺序，不替换 score（RRF 分保留，引用阈值/引用列表零侵入）；② 复用 Chat Provider，无新依赖；③ 失败兜底——缺 key / LLM 抛错 / 返回非 JSON 自动回退 RRF 原顺序；④ Agent 模式每次检索多 1 次 LLM 调用，成本敏感可在设置关
> - **v1.3.1 增量**：query-rewriter 入口加 `stripNoise` 预处理（纯 regex 剥寒暄开头 / 闲聊尾巴 / 句末语气词「呢」），首轮与多轮共享，解决"用户输入有很多无效的词句"稀释检索向量的问题

> **v1.3.0 升级说明**（内部里程碑，公开版仍为 v2.0.0）：查询理解与重写管线（query-rewriter）——替换 v1.2.6 query-resolver，把口语化/短/多意图 query 翻译为 1-3 条可检索 query，RRF 融合后喂给向量库。简单模式 + Agent 模式都覆盖。详见 [§5.7 查询理解与重写管线（v1.3.0）](#57-查询理解与重写管线v130)。
> - **核心修复**：v1.2.6 `query-resolver` 只做"指代消解"（"它/那"→ 实体名）——用户实测反馈「检索时大模型不理解用户语义，很多无效的提示词」，根因是检索侧的 query 质量差：口语化/模糊/短/多意图 query 拿裸 query 直送 embedding + BM25 召回必坏
> - **三件套修复**：
>   - **①query-rewriter 管线**（`src/main/query-rewriter.ts`，~280 行）：用小 LLM（temperature=0.1）一次性产出 `QueryPlan { searchQueries: 1-3 条, intent, expandedTerms }`——自包含原样 / 指代补全 / 模糊扩展（口语化 query 加 2-3 条同义/相关词）/ 多意图分解（"对比 + 区别 + 使用场景" 拆为 2-3 条 sub-query）
>   - **②hybridSearchMultiQuery**（`src/main/vector-store.ts`，~60 行）：与 `hybridSearchMulti` 跨 KB 同构，输入"多 query"而非"多 KB"，多路 fetchK=`max(50, 8×topK)` RRF 全局融合后输出 topK
>   - **③Settings +3 字段**（`enableQueryRewriter` 默认 true / `queryRewriterProviderId` / `queryRewriterModel`）：UI 在「设置 → 常规」加 checkbox + Provider select + Model text input
> - **典型端到端**（用户实测反馈的核心场景）：
>   - 口语化：「这个怎么用啊」→「工具 使用方法 步骤 / 工具 使用教程 / 工具 操作示例」3 条 → RRF 融合 → LLM 看到相关文档
>   - 多意图：「对比 X 和 Y 的区别以及使用场景」→ 分解为 2-3 条 sub-query
>   - 短 query：「限流」→ 扩展为"API 限流策略 / 接口限流配置 / 限流规则说明"
>   - 指代：「第几章？」（上文聊某条例）→「条例名 + 条款编号」
> - **关键设计取舍**：
>   - **替换 query-resolver 而非叠加**——`query-rewriter` 的 `searchQueries[0]` 已包含指代消解能力，叠加会导致每轮 2 次 LLM 调用 + 收益重叠
>   - **多 query 融合而非单 query 拼接**——RRF 融合让 LLM 改写结果不一致时仍能兜底，"q1 OR q2 OR q3" 字符串拼接会让 BM25 稀有词淹没
>   - **失败兜底**——缺 key / LLM 抛错 / JSON 解析失败 / 返回空 → 自动 fallback 到原 query，不影响主流程
>   - **不做 HyDE**——成本高（200+ 字生成）+ LLM 幻觉会污染 embedding，留给未来
> - **升级说明**：v1.2.x 老用户升级后自动切换到 v1.3.0 行为；`enableQueryRewriter` 默认 undefined → 走代码默认 `true`（除非显式存了 false）；`v1.2.5/v1.2.6 query-resolver` 段保留为历史；`Settings.enableQueryRewrite` / `rewriterProviderId` / `rewriterModel` 3 字段（v1.2.2 留下）保留字段定义（兼容老 DB JSON，运行时忽略）
> - **性能影响**：每条 user msg 多 1 次小模型调用（≈300-500 token，温度 0.1）+ 1-3 次额外 `hybridSearch` 检索；首问多 1-3 秒（取决于 KB 大小 / Provider 响应）
>
> **v1.2.7 升级说明**（内部里程碑，公开版仍为 v2.0.0）：preview 截断硬规则——修复 LLM 把截断的 preview 当成完整列表答错的 bug（用户实测：条例"第十三条 (一)~(六)" 答出 (一)~(五) 截止"变更…"）——
> - **核心修复**：v1.2.4 引入 read_chunk 工具流后，检索结果只发"索引 + preview（200 字符）"给 LLM 节省 token。但当源 chunk 是**列举 / 条款 / 编号型**（如"第十三条 (一)~(六)"），200 字符 preview 只能装下前 4-5 条，末尾的省略号 `…` 视觉上像自然结尾，LLM 经常直接基于截断的 preview 答错。v1.2.4~v1.2.6 累积 3 个版本都没显式告诉 LLM "列举型 preview 是被截断的"
> - **三件套修复**：
>   - **①显式 [TRUNCATED] 标记**（`src/main/preview.ts`）：抽 `formatChunkPreview` 跨简单/Agent 模式共享，`hit.text.length > 200` 时显式追加 `[TRUNCATED: 共 N 字...; 列举/条款/编号型内容请先 read_chunk(N)]`，让 LLM 看到截断时**有显式信号**（不再靠猜"…"是不是自然结尾）
>   - **②Citation.chunk 改存全文**：`ipc-handlers.ts` 6 处 + `agent.ts` 2 处把 `c.text.slice(0, 200)` 改 `c.text`——UI 引用块 + readContext 兜底分支用真实全文本（之前是 200 字符 preview，用户看到的引用 + 系统兜底用内容都不完整）；UI 加 `max-h-40 overflow-auto` + `whitespace-pre-wrap` 让长引用能滚+换行
>   - **③硬规则写进 system prompt + tool description**：`SIMPLE_CHAT_SYS_PROMPT` + `AGENT_SYSTEM_PROMPT` + `READ_CHUNK_TOOL.description` 全部把"列举/条款/编号型内容必须 read_chunk"升级为 hard rule（v1.2.4 soft 引导"想看具体内容调 read_chunk"不够强，LLM 把它当可选项，列举型内容必须 hard rule 强约束）
> - **典型场景**：问"条例第二章第十三条前后关于备案事项的完整规定" → 源文档 6 条 `(一)~(六) 设立分支机构` → 新版 AI 会先调 `read_chunk(1)` 拿完整 6 条再答（v1.2.4~v1.2.6 LLM 把 preview 末尾的 `…` 当自然结尾，直接答错漏 (六)）
>
> **v1.2.6 升级说明**（内部里程碑，公开版仍为 v2.0.0）：检索 query 消解去 regex 门控 + agent sub_query 自包含 prompt，彻底解决多轮对话"它/第几章？"类指代召回错的根因——
> - **核心修复**：检索系统（向量库 + BM25）是 **stateless** 的——v1.2.4 把"指代消解"完全寄托给 LLM（"LLM 看到全 history 自然消解"），但**只对 LLM 有效，对检索无效**：`embedText` + `hybridSearch` 发生在 LLM 看 history 之前，拿的是裸 query（"第几章？" / "它的限流策略" / "原文呢"），embedding 和 BM25 不知道历史，召回噪声 → LLM 拿噪声答错。v1.2.5 用 `isAnaphoric` regex 做"是否调 LLM 改写"的 cost gate，但 regex 盖不全开放表达（用户实测："第几章？"的"几"不在表里 / "原文呢" / "适用范围" / "它的限流策略" / "为什么" 等大量真实指代都漏判）。v1.2.6 删 regex 门控改为 **always-LLM 消解**——`session` 有 `history` 总是调小模型（anchor 扩到末 6 条 user/assistant，LLM 自行判断"已自包含 / 需补实体"）
> - **Agent 模式同步修复**：`AGENT_SYSTEM_PROMPT` 加 ⚠ 警示段 + 3 个正反例；`AGENT_TOOLS.search_kb.sub_query.description` 同步更新，LLM 自己生成 sub_query 时显式知道"**必须自包含**"——避免 LLM 直译"第几章？"给 `search_kb`

## 2. 首次启动配置向导

### 2.1 配置 AI 服务
LocalRAG 不会内置任何 API Key，请先准备以下任意一家的账号：
- **OpenAI**（`https://platform.openai.com`）
- **DeepSeek**（`https://platform.deepseek.com`）
- **通义千问 DashScope**（`https://dashscope.aliyun.com`）
- **硅基流动 SiliconFlow**（`https://siliconflow.cn`）

启动后进入「设置」→「AI 服务」：
1. 点击「添加 Provider」
2. 选择服务商，输入显示名
3. 填入 API Key（系统会保存到 Windows 凭据管理器，不会明文落盘）
4. 选择模型（Chat 与 Embedding 可分别设置；v1.1.5+ 还可单独设置 Thinking 模型）
5. 点击「测试连接」

> **重要提示（DeepSeek 用户）**：DeepSeek **没有**原生 Embedding 接口。如果你只用 DeepSeek，上传文档会报 404。需要在「AI 服务」页再新增一个支持 Embedding 的 Provider（OpenAI / 通义千问 / 硅基流动），然后到「设置 → 常规 → Embedding Provider」选它。Chat 仍用 DeepSeek，embedding 走另一家。

### 2.2 选择默认服务
在「设置」→「常规」中，指定：
- 默认 Provider（Chat 走哪家）
- 默认 Chat 模型
- Embedding Provider（向量生成走哪家，留空则与 Chat 共用）

## 3. 创建知识库

1. 左侧栏点击「＋ 新建知识库」
2. 输入名称（如「产品手册」）
3. **填写描述（v1.2.0 推荐）**——简单说清这个知识库装的是什么内容（如「公司前后端代码库的 API 文档与 README」）
4. 点击「创建」

知识库会出现在左侧列表中。

> **v1.2.0 提示**：当你开启 Agent 模式并勾选多个 KB 时，LLM 会读每个 KB 的描述来决定「这个问题应该搜哪些 KB」。描述越准确，跨 KB 检索的效果越好。

## 4. 上传文档

支持格式：`.pdf` / `.docx` / `.md` / `.txt`

1. 在「文档」面板点击「上传文档」或拖拽文件到窗口
2. 选择目标知识库
3. 等待解析与向量化（每 10 页约 3-5 秒）
4. 列表中状态变为「已就绪」即可检索

> **提示**：删除知识库会同时删除其下所有文档与向量，请谨慎操作。

### 4.1 扫描件 / 图片型 PDF（v1.1.6+）

普通 PDF（可复制文字）直接走文本提取。如果你的 PDF 是**扫描件**（文字在图里，搜不到也复制不出来），需要开启 OCR：

1. 「设置」→「常规」→ 勾选「**对扫描件 PDF 启用 OCR**」
2. 首次上传扫描件时，会自动下载 tesseract 中英语言模型（~23MB，**只需下载一次**，之后离线可用，缓存在 `%APPDATA%\LocalRAG\cache\tesseract\`）
3. 识别速度：1-3 秒/页

**OCR 准确率说明**（重要）：
- 中文印刷体、地名 / 地址 / 数字：~85% 准确率
- 公式 / 复杂表格 / 手写体：tesseract 不擅长，识别质量会下降
- 如需更好识别，可手动用专业 OCR 工具先转 PDF → 文本 PDF 再上传

**OCR 排错**：设置页有「**测试 OCR**」按钮——点一下直接初始化 tesseract worker 跑一张内置测试图，告诉你识别耗时 / 结果 / 模型路径，独立验证 OCR 管线是否正常，不依赖任何 PDF。

### 4.2 多个相似文档被引用

如果你上传了 3 个相似主题的文档（比如三份地籍测绘报告），问其中一个内容时三个文档都被引用，是正常的——向量检索按相似度排序，把 top-5 都给了 LLM。解决：

1. 「设置」→「常规」→ 「**引用分数阈值**」
2. 把滑块从默认的 0.4 拉到 0.5-0.6
3. 低于阈值的 chunk 既不进 LLM 上下文、也不展示为引用

> 阈值需要按你用的 embedding 模型微调：OpenAI text-embedding-3 相关文档通常 0.5+；bge-m3 略低。设 0 等于关闭过滤。

### 4.3 切片质量不好？（v1.2.1+）

v1.2.1 起按文件类型自动挑最合适的切分方式，不需要你手动选：

| 文件类型 | 切分方式 | 效果 |
| --- | --- | --- |
| **Markdown** | 结构感知（`marked.lexer`）| 标题层级作为面包屑前缀（`【H1 > H2 > H3】`）；代码块 / 表格作为原子单位（不切散） |
| **PDF（文本层）** | 版面感知（pdfjs 带坐标 items）| 按 (页, y, x) 排版阅读序；自动跳过跨页重复的页眉页脚；段落 / 章节清晰分离 |
| **PDF（OCR / 扫描件）** | 递归分隔符（A+C）| 拿不到版面坐标，退化为按段落 → 句号 → 词的逐级切分 |
| **DOCX / TXT** | 递归分隔符（A+C）| 同上 |

**单位**：v1.2.1 起 `chunkSize` / `chunkOverlap` 单位从**字符改为 token**（cl100k_base）。800 token ≈ 600 中文字 / 2400 英文字。中英文密度差异 ≤ 15%。

**调参建议**：
- 中文文档 + 短答案场景：`chunkSize: 500`、`chunkOverlap: 80`
- 英文长文档 + 代码 / 表格多：`chunkSize: 1200`、`chunkOverlap: 150`
- 想看切分效果：跑 `node scripts/chunker-selftest.js`（开发者工具）

**已知边界**：
- PDF 不做分栏检测——双栏论文 / 期刊章节上下文可能错位。如有需要可手动用专业 OCR 工具先转
- OCR 拿不到版面信息——只能按纯文本走 A+C 切分

### 4.4 追问"它/哪一章？/那关于 X 呢？"没命中？（v1.2.6+）

多轮对话里你问"它是什么意思？"、"哪一章？"、"那关于 X 的呢？"——这些**指代 / 省略**问句的 embed 向量与上一轮实体向量偏离很大，第二轮开始召回率会从 80-90% 跌到 30-50%。**v1.2.6 起自动处理**（always-LLM 消解）：

> ⚠ **重要提示（v1.2.4 → v1.2.6 关键修复）**：检索系统（向量库 + BM25）是 **stateless** 的——`embedText` + `hybridSearch` 发生在 LLM 看 history 之前。v1.2.4 "LLM 看到完整 history 自然消解" **只对 LLM 端有效，对检索端无效**——LLM 拿到的是 embedding 召回的噪声 context，即便消解也救不回已被污染的检索。v1.2.6 修复：**检索前**先调小模型把 `current + 末 6 条 history` 凝成 self-contained 检索 query，结果**只喂 `embedText` + `hybridSearch`**（不进 LLM context，LLM 反正自己看 history 也能消解）

- **简单模式**：`session` 有 `history` → 总是调小模型（≈200-300 token，温度 0.1）消解；anchor 是末 6 条 user/assistant（≈3 轮），LLM 能看到前一轮 assistant 答案里的实体名
- **Agent 模式**：`AGENT_SYSTEM_PROMPT` 显式告诉 LLM "**sub_query 必须自包含**" + 3 个正反例
- 例：Q1 "《北京市殡葬管理条例》第十四条的内容是什么" → Q2 "**第几章？**" → 检索前 LLM 消解为 "北京市殡葬管理条例 第十四条" → embedding 命中该条所属章节的 chunk → LLM 答对

不需要任何配置，默认开启。详见 [§5.5 多轮检索消解（v1.2.6）](#55-多轮检索消解v126)。

### 5.3 Agent 模式（v1.2.0）

Agent 模式让 LLM 自己决定「要不要检索、检索什么、检索几次、检索结果够不够」，能处理比简单模式更复杂的问题（跨 KB、查询分解、多轮迭代）。

#### 5.3.1 启用

1. 「设置」→「常规」→ 勾选「**启用 Agentic RAG**（多步推理 + 跨 KB）」
2. 顶部「**对话**」区会出现一个「**🧠 Agent** / **⚡ 简单**」切换按钮——点它可在两种模式间切换
3. 默认值跟随「设置」开关；随时可手动覆盖

> 任何 OpenAI 兼容的 Provider 都支持（OpenAI / DeepSeek / 通义千问 / 硅基流动）。**DeepSeek 的 `deepseek-chat` 完全支持 function_calling**。

#### 5.3.2 跨 KB 检索

1. 左侧 KB 列表勾选多个 KB（多选 checkbox）
2. 顶部 header 会出现「**跨 N KB**」徽章
3. 输入问题后，Agent 会先把「KB 目录 + 你的问题」喂给 LLM，让它挑该搜哪些 KB，然后只在挑中的 KB 里检索
4. 回答会同时引用多个 KB 的内容

#### 5.3.3 看 Agent 的思考过程

Assistant 回答上方有一个**可折叠**的面板：「🧠 Agent 思考（5 步）」：
- 点击展开能看到完整的思考步骤：plan → search → search → critique → final
- 每步显示：用的工具名、检索词、命中 KB、召回片段数、单步耗时
- 流式回答时面板会实时增长，并显示当前阶段（`planning` / `searching` / `critiquing` / `finalizing`）

#### 5.3.4 适用场景 vs 不适用

| 场景 | 推荐模式 | 原因 |
| --- | --- | --- |
| 「这份 PDF 第 3 节讲什么？」 | 简单 | 单 KB、单次检索够用 |
| 「对比 PG 和 Mongo 的事务机制和索引」 | Agent | 需拆成 2-3 个子问题分别检索 |
| 「前后端哪个用 React？」（已勾多个 KB） | Agent | LLM 自选 KB |
| 「你好 / 1+1」 | Agent 会自动调 `skip_search` | 直接通识答 |
| 「重写这段代码」 | 简单 | 与 KB 无关 |
| 「上次讨论的 API 限流方案第 3 步怎么实现？」 | Agent | 可能需要改写查询再搜 |

#### 5.3.5 性能与降级

- **首问慢 2-5 秒**——agent 模式要多轮 LLM 调用（plan → search → critique → final）。简单模式秒回
- **Provider 不支持 tools**——自动降级到简单模式（embed + 单 KB 检索 + 流式生成），主进程 log warning
- **遇到报错**——降级不影响功能，只是少了 agent 的多步能力

#### 5.3.6 Agent 相关设置

| 设置 | 默认值 | 说明 |
| --- | --- | --- |
| 启用 Agentic RAG | 关 | 总开关；关闭时与旧版（v1.1.6）行为完全一致 |
| KB 自选 | 开 | Agent 会先让 LLM 挑 KB；关闭时直接全选所有勾选的 KB |
| 最大循环次数 | 4 | LLM 最多「检索→评估」几次。超过自动进入「基于已收集资料直接回答」 |
| 每次检索片段数 | 5 | 每个子问题召回的片段数（多 KB 融合后取 topK） |

### 5.4 对话上下文智能（v1.2.4）

v1.2.4 重新设计了对话上下文：**清理 v1.2.2 query rewriting 过度设计** + **智能 context 截断** + **read_chunk 工具按需取片段**。所有功能**默认开启**，不需要任何操作就能用。

#### 5.4.1 智能 context 截断（`buildHistory`）

**问题**：v1.2.2 改写 LLM 每条 user 消息多 1 次调用；v1.2.3 硬切 `slice(-8)` 太短；多轮 RAG 指代问句召回差。

**v1.2.4 修复**：

- **直接给 LLM 完整 history**——让 LLM 自己脑补"它"指代什么（只要 LLM 看得到上文）
- **按模型 context window 智能截断**——`buildHistory` 算总 token，能塞下就全塞（64K 模型约 40 turn 内不触发）；超了才 firstUser 必带 + 中间调 LLM 压缩 + 末尾尽量多
- **跨 session 摘要召回保留**——v1.2.3 的"我们之前聊过 X 吗"能力沿用，注入到 system prompt 之前

**效果**：

| 模型 context window | 触发截断的 turn 数（粗估） |
| --- | --- |
| gpt-4o-mini 128K | ~80 turn |
| deepseek-chat 64K | ~40 turn |
| qwen-turbo 1M | 几乎不触发 |
| gpt-4 8K（旧模型） | ~5 turn |

#### 5.4.2 read_chunk 工具（v1.2.4）

**问题**：旧行为检索 topK=5 全文塞 LLM context（5×800=4000 token），前 1-2 段就够回答，后 3-4 段全在浪费 token。

**v1.2.4 修复**：

- **检索后只发"索引 + preview"**——每条 200 字 preview + score + filename（5×200=1000 token）
- **LLM 按需调 `read_chunk(chunk_id)`** 拉完整内容（实际读 1-2 段，按需 200-1000 token）
- **节省 60-80% chunk 相关 token**——简单模式（`Settings.enableReadChunkTool` 默认开）和 Agent 模式统一

**效果**：

| 模式 | 旧行为（v1.2.3） | 新行为（v1.2.4） |
| --- | --- | --- |
| 简单模式 | topK=5 全文（4000 token） | 5×200 preview（1000 token）+ LLM 读 1-2 段 |
| Agent 模式 | `search_kb` 工具响应内嵌全文 | `search_kb` 只返回 preview + ID + score |

#### 5.4.3 相关设置

| 设置 | 默认值 | 说明 |
| --- | --- | --- |
| 简单模式按需读片段 | 开（v1.2.4+） | `enableReadChunkTool` —— 检索后只发 preview，LLM 按需 `read_chunk` 取全文。关闭退回 topK 全文（适合 Provider 不支持 function_calling） |
| 周期摘要阈值 | 20 | v1.2.3+ 沿用。每 20 turn 触发一次 `session_summaries` 落库，跨 session 用 SQL LIKE 召回。填 0 关闭 |

> **v1.2.4 删除的设置**：v1.2.2 的「启用查询改写」「改写 Provider」「改写模型」3 个设置项在 v1.2.4 已移除（被 `buildHistory` 替代）。老 DB JSON 里的字段会被忽略。

#### 5.4.4 性能

- **智能截断 0 额外调用**——能塞下时全 history 0 调用
- **read_chunk 工具流**——简单模式最多 1 轮 read_chunk；Agent 模式由 `agentMaxIterations` 限制
- **LLM 看到全 history 0 假阳性**——指代 / 省略靠 LLM 自然消解，不再有 ANAPHORIC_RE 误判
- **Provider 不支持 function_calling**——read_chunk 自动降级到 topK 全文，行为兼容
- 不想异步调 LLM 跑摘要？「设置 → 常规 → 周期摘要阈值」填 0

### 5.5 多轮检索消解（v1.2.6）

**问题**：多轮对话里你问"它是什么意思？"、"哪一章？"、"那关于 X 的呢？"——这些**指代 / 省略**问句的 embed 向量与上一轮实体向量偏离很大，第二轮开始召回率从 80-90% 跌到 30-50%。

**v1.2.4 → v1.2.6 关键认知**：检索系统（向量库 + BM25）是 **stateless** 的——`embedText` + `hybridSearch` 发生在 LLM 看到 history 之前。**v1.2.4 "LLM 看到完整 history 自然消解" 只对 LLM 端有效，对检索端无效**——LLM 即便消解也救不回已被污染的检索 context。**v1.2.5 用 regex 做"是否调 LLM 改写"的 cost gate，但 regex 盖不全开放表达**（用户实测："第几章？"的"几"不在表里 / "原文呢" / "适用范围" / "它的限流策略" / "为什么" / "详细说说" 等大量真实指代都漏判）。

**v1.2.6 修复**（两层互补）：

1. **检索端**（**新增**，核心修复）：`src/main/query-resolver.ts` 在 `runSimpleChat` 检索**前**先调小模型（≈200-300 token，温度 0.1）把"current + 末 6 条 user/assistant history"凝成 self-contained 检索 query，结果**只喂 `embedText` + `hybridSearch`**（不进 LLM context，LLM 反正自己看 history 也能消解）
   - **always-LLM**：session 有 history **总是**调（v1.2.5 是 regex 命中才调）——误判率太高，漏的 case 后续会被用户重复触发，always-LLM 在 multi-turn 总成本更低
   - **anchor 扩到 6 条**：v1.2.5 是"末条 user msg"；v1.2.6 是"末 6 条 user/assistant"（≈3 轮）——LLM 能看到前一轮 assistant 答案里的实体名
2. **LLM 端**（`AGENT_SYSTEM_PROMPT` 显式要求）：Agent 模式 `sub_query` 由 LLM 自己生成，v1.2.6 在 prompt 顶部加 `⚠ 调 search_kb 之前：sub_query 必须自包含` 警示段 + 3 个正反例（北京市殡葬管理条例 / OpenAI API / 5G vs 4G），LLM 看到后自动替换指代为实体名

**典型场景**：

| 用户输入 | 旧行为（v1.2.4 / v1.2.5） | 新行为（v1.2.6） |
| --- | --- | --- |
| "第几章？"（上文聊《北京市殡葬管理条例》第十四条） | LLM 知道指代前文，但 embedding 拿到"第几章？"召回全 KB 噪声（中医/动物防疫/科创中心）→ LLM 答错 | 检索前 LLM 改写为"北京市殡葬管理条例 第十四条" → embedding 命中该条所属章节的 chunk → LLM 答对 |
| "它的限流策略呢"（上文聊 OpenAI API） | v1.2.5 `isAnaphoric` 命中（"它"在表里）→ 调 LLM 改写为"OpenAI API 限流策略" | 同样改写，结果一致 |
| "5G 和 4G 的区别"（自包含） | v1.2.4 LLM 自己消解（无指代）| v1.2.6 走 passthrough（无 history 或自包含），0 LLM 调用 |
| Agent 模式 + "第几章？" | v1.2.4 Agent 模式下 LLM 直译"第几章？"给 `search_kb` → 同样噪声 | `AGENT_SYSTEM_PROMPT` ⚠ 警示 → LLM 自动生成 `sub_query="北京市殡葬管理条例 第十四条"` → search_kb 命中正确 chunk |

**性能**：
- 每条 multi-turn user msg 多 1 次 chatCompletion（≈200-300 token 小模型，温度 0.1，单次 ≈ 200ms 延迟）——与 v1.2.2 的 query rewriting 同档
- 进程内缓存 `Map<key, ResolvedQuery>`（key 含 `currentUserMsgId` 避免"同 query 不同 turn 拿到陈旧 resolved"）——同 query 二次调 0 LLM 调用
- 缺 Chat Provider API Key / LLM 抛错 / 返回空 / 返回同 query → 全部 fallback 原文，**不阻塞**主流程
- **取舍**：v1.2.5 的"先 regex 判断再决定调不调"看似省 LLM 调用，但误判率太高，漏的 case 后续被用户重复触发，always-LLM 在 multi-turn 总成本更低

**升级说明**：
- 全部默认开启，无需任何操作
- v1.2.5 老用户升级：自动切换到 always-LLM；`isAnaphoric` / `stripQuestionTail` 删除不影响 DB（无对应 settings 字段）
- v1.2.2 老用户升级：`Settings.enableQueryRewrite` / `rewriterProviderId` / `rewriterModel` 3 字段保留**字段定义**（兼容老 DB JSON，运行时忽略）

**已知边界**：
- always-LLM 在多轮会话里多 N 次小模型调用（与 v1.2.2 的 query rewriting 同档）
- 缺 Chat Provider API Key 时所有有 history 的 query 都 fallback 原文
- cache key 含 `currentUserMsgId`——同 query 不同 turn 不会复用

### 5.6 preview 截断硬规则（v1.2.7）

**问题**：你问"条例第二章第十三条前后关于备案事项的完整规定"——源文档 6 条 `(一)~(六) 设立分支机构`，AI 答出 (一)~(五) 截止到"变更…"，漏答 (六)。**v1.2.4~v1.2.6 累积 3 个版本都没显式告诉 LLM "列举型 preview 是被截断的"**——LLM 看到 preview 末尾的省略号 `…` 视觉上像自然结尾（不是被截断），直接基于截断的 preview 答错。

**v1.2.7 修复**——三件套：

1. **①显式 `[TRUNCATED: 共 N 字...]` 标记**（`src/main/preview.ts` 抽 `formatChunkPreview` 跨简单/Agent 模式共享）：`hit.text.length > 200` 时显式追加 `[TRUNCATED: 共 N 字，仅显示前 200 字；列举/条款/编号型内容请先 read_chunk(${chunkId}) 取完整内容再引用]`——让 LLM 看到截断时**有显式信号**（不再靠猜"…"是不是自然结尾）
2. **②Citation.chunk 改存全文**：`ipc-handlers.ts` 6 处 + `agent.ts` 2 处把 `c.text.slice(0, 200)` 改 `c.text`——UI "引用来源"展开的内容 + 系统兜底（readContext）用真实全文本（之前是 200 字符 preview，用户看到的引用 + 系统兜底用内容都不完整）；UI 加 `max-h-40 overflow-auto` + `whitespace-pre-wrap` 让长引用能滚+换行
3. **③硬规则**（`SIMPLE_CHAT_SYS_PROMPT` + `AGENT_SYSTEM_PROMPT` + `READ_CHUNK_TOOL.description` 全部升级）：把"列举/条款/编号型内容必须 read_chunk"从 soft 引导（v1.2.4 的"想看具体内容调 read_chunk"——LLM 把它当可选项）升级为 hard rule——
   - **典型格式**：(一)(二)(三) / 第N条/章/款 / 1.1.2 / A. B. C. / `- 列表项`
   - **规则**：preview 末尾出现 `[TRUNCATED: 共 N 字...]` 标记 且 内容看起来像列举/条款/编号型 → **必须先调 read_chunk(N) 拿完整内容再引用**

**典型场景**：

| 用户输入 | 旧行为（v1.2.4~v1.2.6） | 新行为（v1.2.7） |
| --- | --- | --- |
| 问"条例第十三条前后完整规定" | preview 装下 (一)~(五) + "（八）其…" → LLM 把省略号当自然结尾 → 答 (一)~(五) 截止"变更…"漏 (六) | preview 末尾显式 `[TRUNCATED: 共 280 字...; 列举型内容请先 read_chunk(1)]` → 硬规则命中 → LLM 调 `read_chunk(1)` 拿完整 6 条 → 答 (一)~(六) |
| 问"API 错误码列表" | preview 装下 5 条 + "…" → LLM 答出 5 条漏尾部 | 同上硬规则 → LLM 读全文 → 答出全部 |
| 引用来源展开 | 显示 200 字符 preview（截断在中间） | 显示真实 chunk 全文本（带换行 + 滚动条） |

**已知边界**：
- preview 仍 200 字符（节省 token 不动）；v1.2.7 改的是"告诉 LLM 这是截断的方式"
- 边界 200 字不加 TRUNCATED（200 字符已经全显示）/ 边界 201 字加 TRUNCATED——自检脚本验证
- 偶尔 AI 仍漏项（极少见）→ ①展开"引用来源"查看完整内容；②追问时显式说"请用 read_chunk 拿完整内容再回答"

### 5.7 查询理解与重写管线（v1.3.0）

v1.3.0 把 v1.2.6 的「query-resolver 单一指代消解」升级为完整管线——用 LLM 把口语化/短/多意图 query 翻译为 1-3 条高质量可检索 query，多 query 走 RRF 融合后喂给向量库。简单模式 + Agent 模式都受益。

**问题**：用户实测反馈「检索时大模型不理解用户语义，很多无效的提示词」——
- 口语化 / 模糊 query（「这个怎么用啊」「那个报错怎么办」）：embedding 找不到明确向量
- 短 query（「限流」「价格」）：BM25 没有足够上下文命中
- 复杂多意图 query（「对比 X 和 Y 的区别，以及各自的使用场景」）：一个 query 拉不回两边片段
- 多轮指代 / 省略 query（v1.2.6 query-resolver 已处理「它/那」→「实体名」）

**修复——`query-rewriter` 三件套**：

1. **新建 `src/main/query-rewriter.ts::planSearchQuery()`**（~280 行）—— 用小 LLM（temperature=0.1）一次性产出 `QueryPlan { searchQueries: 1-3 条, intent, expandedTerms, needsHighRecall }`：
   - **自包含原样**（"5G 和 4G 的区别" → searchQueries: [原 query]，1 条）
   - **指代补全**（"第几章？" + 上文聊《北京市殡葬管理条例》第十四条 → searchQueries: ["北京市殡葬管理条例 第十四条"]，1 条）
   - **模糊扩展**（"这个工具怎么用" → searchQueries: ["工具 使用方法 步骤", "工具 使用教程", "工具 操作示例"]，3 条）
   - **多意图分解**（"对比 X 和 Y 的区别以及使用场景" → searchQueries: ["X 特性", "Y 特性", "X 和 Y 区别"]，3 条）

2. **`vector-store.ts::hybridSearchMultiQuery()`**（~60 行）—— 与 `hybridSearchMulti` 跨 KB 同构，区别是输入"多 query"而非"多 KB"。单 query 退化为 `hybridSearch` fastpath。每路 fetchK = `max(50, 8×topK)`，多路 RRF 融合后输出 topK

3. **`runSimpleChat` / `runAgent` 都接入**：
   - 简单模式：planSearchQuery 产出 1-3 条 → 并发 embed → hybridSearchMultiQuery RRF 融合 → topK 给 LLM
   - Agent 模式：planSearchQuery 产出 → 把 `plan.searchQueries` 拼到 system prompt 作为「已改写候选 query（供参考）」——LLM 仍可自主调 `search_kb` 输出 sub_query，但有更好的起点

**关键设计取舍**：

- **替换 query-resolver（v1.2.5/v1.2.6）**——`query-rewriter` 的 `searchQueries[0]` 已包含指代消解能力，叠加会导致每轮 2 次 LLM 调用 + 收益重叠
- **多 query 融合而非单 query 拼接**——RRF 融合让 LLM 改写结果不一致时仍能兜底，"q1 OR q2 OR q3" 字符串拼接会让 BM25 稀有词淹没
- **Agent 模式预计算 plan 但不强制使用**——LLM 仍可自调 search_kb，plan 仅作"参考起点"
- **失败兜底**：缺 key / LLM 抛错 / JSON 解析失败 / 返回空 → 自动 fallback 到原 query，不影响主流程
- **不做 HyDE**——成本高（200+ 字生成）+ LLM 幻觉会污染 embedding，留给未来

**典型端到端**：
- 旧行为（v1.2.6）：用户问「这个工具怎么用啊」（口语化模糊）→ query-resolver 看到无指代 → passthrough 原 query → embedding 找到"工具怎么用"通用文档 → 答非所问
- 新行为（v1.3.0）：query-rewriter 看到有 history → 调 LLM → 扩展为 ["工具 使用方法 步骤", "工具 使用教程", "工具 操作示例"] 3 条 → RRF 融合 → LLM 看到用户具体工具名相关文档 → 准确回答

**已知边界 / 留给未来**：
- always-LLM 改写每条 user msg 多 1 次小模型调用（≈300-500 token，温度 0.1）+ 1-3 次额外 `hybridSearch` 检索
- KB 大（10K+ chunks）时检索阶段 +200-500ms；用户感知：首问多 1-3 秒
- `enableQueryRewriter=false` 一键退回 v1.2.6 行为
- `queryRewriterProviderId/Model` 可指定便宜模型（Qwen-Turbo / gpt-4o-mini）
- HyDE / cross-encoder rerank：v1.4.0+ 评估
- BM25 term boost（用 `expandedTerms`）：Plan 字段预留，UI 不暴露

### 5.8 检索结果重排（v1.3.2）

v1.3.2 在检索后、构造 LLM 上下文前插入一步 **LLM rerank**——召回扩大到 20 候选 → Chat Provider 小 LLM 按语义相关度重排 → 取 topK 喂主答 LLM。解决「正确答案被 BM25/RRF 排到 topK 外」。

**背景**：v1.2.8/v1.2.9 调过 BM25/RRF 参数（topK 5→8、RRF_K 60→30、b 0.75→0.5）但没根治。用户实测复现「北京历史文化名城保护条例 第二章第十三条前后备案事项」：BM25 把正确答案（chunk 7 含第十九-二十二条）排到 rank 12，8 个整章 chunk 的 BM25 分数挤在 10% 区间内（29.97/27.04/26.81/...），区分度极低；RRF 融合后答案落到 rank 6 边缘，topK 切掉，LLM 拿到整章总则 chunk 幻觉出"第四章只有第三十四条"。根因：BM25 中文 unigram 分词让条例名前缀（每章节 chunk 都以「北京历史文化名城保护条例 第N章」开头）稀释 IDF，整章 chunk tf 命中关键词次数多 → 分高；继续调参边际递减。

**修复**（`src/main/reranker.ts::rerankHits`）：
- 复用 Chat Provider + chatModel（同 summary/rewriter），无新依赖
- 候选上限 20（防 prompt 爆），≤1 hit 不调 LLM
- prompt 让 LLM 输出 `{"order":[编号降序]}`，按 order 重排，未列入的按 RRF 原顺序追加末尾
- **只重排顺序，不替换 score**（RRF 分保留，引用阈值/引用列表零侵入）
- 失败兜底：缺 key / LLM 抛错 / 返回非 JSON / 空 order → 自动回退 RRF 原顺序

**典型端到端**：
- 旧行为（v1.2.9）：问"第二章第十三条前后备案事项" → BM25 rank 12 / RRF rank 6 的正确答案被 topK=8 切掉 → LLM 拿到整章总则 chunk → 幻觉"第四章只有第三十四条"
- 新行为（v1.3.2）：扩召回到 20 → rank 6 答案进候选池 → LLM 看语义重排 → 答案抬到前 1-2 → LLM 优先看到正确 chunk → 完整列出 (一)~(六)

**已知边界 / 留给未来**：
- Agent 模式每次 search_kb 多 1 次 LLM 调用（成本敏感可在设置关 `enableRerank`）；简单模式每问多 1 次（~几百 token，温度 0.1）
- rerank 候选上限 20——更大候选池会让 prompt 变长、变慢；20 是经验值
- 按条切片（根治 BM25 tf 稀释的另一条路）：留 v1.4.0+ 评估

**v1.3.3 增量：rerank 启用时直接发全文**

v1.3.2 rerank 把正确 chunk 搜到了，但用户实测仍答截断——AI 说"被截断，暂不支持拉取完整文档"只答 (一)。根因：简单/agent 模式都走 read_chunk preview 流（v1.2.4）——chunk 全文 > 200 字时只发前 200 字 preview + `[TRUNCATED]` 标记，依赖 LLM 主动调 `read_chunk` 拿全文。v1.2.7 硬规则"列举/条款型必须先 read_chunk"对弱模型无约束力——LLM 没调工具就直接用 preview 答（程序兜底），编"暂不支持拉取"借口。

v1.3.3 修复：**rerank 启用时跳过 read_chunk preview 流，直接发 topK 全文**。rerank 已精确挑出语义最相关 chunk，全文成本可接受（topK=8 约 6.4K token），且不再依赖 LLM 主动调工具。rerank 关闭时保持 read_chunk 流（无 rerank 时 chunk 质量参差，LLM 选择性读省 token 有价值）。无新增设置（绑定 `enableRerank`）。

### 5.9 检索性能优化（v1.3.5）

v1.3.5 解决简单模式慢的问题。加 分步耗时日志后定位到 **rerank 33 秒**是主凶——deepseek-v4-flash 非流式响应（`chatCompletion` `stream:false`）要等思考链+正文全生成完才一次性返回，10-33s 超时。

**修复（三件套）**：
- **分步耗时日志**：`[chat] [timing] session=... plan=Xms embed=Xms search=Xms rerank=Xms hits=N` + `total=Xms`。定位慢在哪步
- **rerank/plan 改流式**：LLM 调用从 `chatCompletion`（非流式）改成 `chatStream`（流式），正文一出就能收，思考链边来边丢。**实测 rerank 33s→3.7s**；plan 4s 没降（真思考时间，流式省不了）
- **rerank 10s 超时兜底**：超时回退 RRF 原顺序，最差 10s 而不是 33s

**关键认知**：流式加速 = 省掉服务端缓冲 + 避免思考链憋超时，**不是省"生成时间"**。rerank 33s→3.7s 立竿见影是因为之前 33s 大部分是非流式缓冲/超时浪费；plan 4s 是真思考，流式省不了。

**剩余瓶颈**：plan 4s（多轮才发生，真思考时间）、embed 1.9s（单次 embedding API，优化空间小）。这些要再降只能简化 prompt 或换更快模型，流式帮不了。

### 5.10 闲聊短路（v1.3.4）

v1.3.4 让"你好/谢谢/在吗"等闲聊跳过检索直接主答，省 2-3 次 LLM/API 调用。

- **首轮**（无 history）：cheap regex 检测纯问候（≤8 字、整句就是问候），零 LLM 成本。极保守——含疑问/实义内容的不命中
- **多轮**（有 history）：LLM 判断"是否需要检索"，拿不准一律 false（宁可检索别漏答）
- **失败兜底**：LLM 抛错/非 JSON → 当普通问题走检索

**会话等待串扰修复**（同 v1.3.4）：修复"一个会话提问时切到别的会话也显示等待"——切会话时若切到的不是正在流式的会话，清流式态（新会话干净）；切回正在流式的原会话不动（token 续上不丢内容）。

## 7. 常见问题

**Q1：启动后弹出「向量库启动失败」？**
A：本版本（v1.1+）使用纯 JS 向量库 vectra，不再有"启动失败"对话框。若遇到索引错误，可删除 `%APPDATA%\LocalRAG\index\` 目录后重启应用（会触发重建）。

**Q2：API Key 在哪保存？**
A：Windows 凭据管理器（控制面板 → 用户账户 → 凭据管理器 → Windows 凭据）。**不会**以明文保存到任何文件。

**Q3：能否离线使用？**
A：上传过的文档和已生成的向量数据完全离线可用；对话需要联网调用 Chat API；首次启用 OCR 需联网下载 ~23MB tesseract 模型，之后离线可用。

**Q4：上传超大 PDF 怎么办？**
A：建议拆分后分批上传；单文件超过 200 MB 可能被系统 OOM 杀死。

**Q5：如何彻底卸载？**
A：控制面板 → 卸载程序。卸载时可选择「同时删除数据目录」以清空所有知识库。

**Q6：能否更换数据存储位置？**
A：可以通过快捷方式的「目标」追加 `--user-data-dir="D:\MyRagData"`。

**Q7：知识库数据怎么备份？**
A：备份整个 `%APPDATA%\LocalRAG\` 目录即可（包含 SQLite 数据库 + 向量索引 + 配置 + 缓存）。注意 API Key 存在 Windows 凭据管理器，备份目录里不包含。

**Q8：与之前版本的 ChromaDB 版本能共存吗？**
A：不能。两套数据格式不同。升级到 v1.1 后需要重新上传文档。

**Q9：上传扫描件 PDF 提示「文档内容为空或无法解析」？**
A：先到「设置 → 常规」勾选「**对扫描件 PDF 启用 OCR**」。开启后纯文字提取失败的 PDF 会自动 fallback 到 tesseract OCR（首次需联网下载模型）。如果还是不行，点「**测试 OCR**」按钮独立验证——不依赖任何 PDF，直接用 canvas 画测试图丢给 OCR 引擎。

**Q10：上传 DeepSeek 用户专属文档后报 404？**
A：DeepSeek 没有 `/embeddings` 接口（任何模型都 404，这是 DeepSeek 的根本限制）。在「AI 服务」页新增一个支持 Embedding 的 Provider（OpenAI / 通义千问 / 硅基流动），然后到「设置 → 常规 → Embedding Provider」选它。Chat 仍可继续用 DeepSeek。

**Q11：删除文档后文档数变负数？**
A：v1.1.6 起已修复（`updateKBStats` 改为条件回退 + 启动时按 documents 表实际重算）。如果是从更老版本升上来的，删除/重命名知识库即可触发重算；或者直接重启应用一次。

**Q12：引用分数阈值怎么调？**
A：默认值 0.4（OpenAI 模型的常见起点）。如果你看到「问一个文档、三个文档都被引用」的现象，把阈值拉高到 0.5-0.6；如果你觉得回答忽略了相关文档，把阈值降到 0.3-0.35。embedding 模型不同分数分布差异大，需要按实际情况微调。

**Q13：Agent 模式是什么？和「简单模式」有什么区别？（v1.2.0+）**
A：简单模式是「单次检索 + 一次性生成」——一个问题只搜一次，LLM 直接答。Agent 模式是「多轮迭代 + 自主决策」——LLM 拿到第一次检索结果后，会判断信息够不够：够就直接答，不够就改写查询再搜，可能搜 2-3 次。Agent 模式还支持「跨 KB」：把多个 KB 一起勾上，LLM 自己挑该搜哪些（依据是 KB 描述）。**Agent 模式首问慢 2-5 秒**。简单模式推荐用于：单 KB、问题简单、要秒回；Agent 模式推荐用于：跨 KB、查询需要分解、检索结果可能不全。

**Q14：Agent 模式开启后 Provider 报 400/422 怎么办？**
A：v1.2.0 起会自动降级——agent 模式失败后回退到简单模式（embed + 单 KB 检索 + 流式生成），主进程 log warning。你不会看到任何错误，只是少了 agent 的多步能力。所有 OpenAI 兼容 Provider（OpenAI / DeepSeek / 通义千问 / 硅基流动）都支持 function_calling，理论上不会触发降级。

**Q15：怎么给 KB 写一个好的描述？（v1.2.0+）**
A：当你开启 Agent 模式并勾选多个 KB 时，LLM 会读每个 KB 的 `description` 字段来决定「这个问题该搜哪些 KB」。好的描述应该用一两句话说清「**这里装的是什么**」。比如：
- ✓ 「公司订单系统的后端代码 + 数据库 schema 文档」
- ✓ 「产品手册（2024 版）— 功能列表、操作流程」
- ✗ 空着
- ✗ 「知识库」（太泛，没区分度）

**Q16：v1.1.6 升级到 v1.2.0 后旧数据还在吗？**
A：在。数据库自动迁移：给 `messages` 表加 3 列（`agent_trace` / `tool_call_id` / `name`）；旧消息没这些列就是 null，UI 正常显示。向量索引无需重建。Agent 模式默认关闭，保持旧行为完全一致。

**Q17：追问"它/哪一章？/那关于 X 呢？"答非所问怎么办？（v1.2.6+）**
A：v1.2.6 起已用 **always-LLM 检索消解**彻底修复。**v1.2.4 之前（包括 v1.2.5）的修复不彻底**——LLM 端能看到 history 自己消解，但检索系统（向量库 + BM25）拿的是裸 query，embedding/BM25 召回全 KB 噪声，LLM 拿噪声答错。本版本修复：检索**前**先调小模型（≈200-300 token，温度 0.1，anchor 是末 6 条 user/assistant）把"current + 末 6 条 history"凝成 self-contained 检索 query，结果**只喂 `embedText` + `hybridSearch`**（不进 LLM context）。Agent 模式同步在 `AGENT_SYSTEM_PROMPT` 加 ⚠ 警示 + 3 个正反例。
- **核心场景**（用户实测）：上文聊《北京市殡葬管理条例》第十四条 → 追问"第几章？" → 改写为"北京市殡葬管理条例 第十四条" → embedding 命中该条所属章节的 chunk → LLM 答对
- **必读**：v1.2.4 的 `buildHistory` 仍保留（让 LLM 看到完整 history，对 LLM 端消解有效）；v1.3.0 的 `query-rewriter` 在**检索端**独立工作（让 embedding/BM25 拿到高质量可检索 query）——两层是互补的
- 想看是不是真在改写：开发模式下可以观察主进程日志：
  - 简单模式：`[chat] [query-plan] intent=... queries=N steps=[...] "原 query..." → "改写 1...", "改写 2"...`
  - Agent 模式：`[agent] session=xxx query-plan intent=... queries=N steps=[...] ...`
- 关闭 read_chunk 工具流不影响消解（消解发生在检索前）

**Q18：长 session（> 40 turn）history 越界、跨 session 答不上"我们之前聊过 X 吗"？（v1.2.4+）**
A：v1.2.4 起已自动处理：
- **session 内 history 越界**：`buildHistory` 按模型 context window 智能截断，DeepSeek-V3 64K 约 40 turn 内不触发压缩，GPT-4o 128K 约 80 turn
- **跨 session 记忆**：每 20 轮（默认）自动生成对话摘要落库（**fire-and-forget，不阻塞聊天**）；发问时从 `session_summaries` 表 SQL LIKE 命中 top 2 历史摘要注入到 LLM 上下文
- **想关闭摘要**：「设置 → 常规 → 周期摘要阈值」填 0 即可
- **想加速摘要生成**：把摘要阈值调到 10（更频繁触发，但 token 消耗也更多）
- **摘要 token 消耗**：每次 ~1-2K（输入 history + 输出 200-400 字 summary），用 cheap 模型成本很低

**Q19：周期摘要失败会有影响吗？**
A：不会。摘要是 fire-and-forget（后台异步），失败 `console.warn` 后跳过；下次 user 消息再试。**用户感知不到任何错误**——失败的摘要只是漏了一次，跨 session 召回少一段信息，聊天本身完全正常。

### Q20：AI 回答的列举 / 条款 / 编号型内容漏了尾部项怎么办？（v1.2.7+）

**Q**：我上传了一个条例 PDF，里面有 6 条 `(一)~(六) 设立分支机构`，我追问"前后关于备案事项的完整规定"——AI 答出 (一)~(五) 截止到"变更…"，漏答 (六)。原文 6 条都在，preview 怎么就截了？

**A**：v1.2.4 引入 `read_chunk` 工具后，**检索结果只发"索引 + preview（200 字符）"**给 LLM 节省 token。源 chunk 长 280 字符时，preview 装下 (一)~(五) + "（八）其…"，末尾的省略号 `…` 视觉上像自然结尾，**LLM 经常直接基于截断的 preview 答错**——v1.2.4~v1.2.6 累积 3 个版本都没显式告诉 LLM "列举型 preview 是被截断的"。

**v1.2.7 起自动处理**——三件套防护：
- **①显式 `[TRUNCATED: 共 N 字...]` 标记**：preview 末尾加显式信号 + `read_chunk(N)` 指引，LLM 看到截断时不再靠猜
- **②Citation.chunk 存全文**：UI "引用来源"展开的内容 + 系统兜底用真实 chunk 全文本（之前是 200 字符 preview）
- **③硬规则**：`SIMPLE_CHAT_SYS_PROMPT` / `AGENT_SYSTEM_PROMPT` / `READ_CHUNK_TOOL.description` 全部把"列举/条款/编号型内容必须 read_chunk"升级为 hard rule

不需要任何配置，默认生效。**遇到特殊情况**（AI 偶尔仍漏项）：①展开"引用来源"查看完整内容（v1.2.7 已是全文）；②追问时显式说"请用 read_chunk 拿完整内容再回答"——LLM 会立即调工具。

详见 [§5.6 preview 截断硬规则（v1.2.7）](#56-preview-截断硬规则v127)。

### Q21：检索时大模型不理解我的问题，召回的文档不相关怎么办？（v1.3.0）

**A**：v1.3.0 起，「设置 → 常规」默认勾选「**查询改写 / 扩展**」——每条 user 消息在检索前会用一个小 LLM 把口语化 / 模糊 / 短 / 多意图 query 翻译为 1-3 条可检索 query（指代补全 / 模糊扩展 / 多意图分解），多 query 走 RRF 融合后喂给向量库。简单模式 + Agent 模式都受益。

**典型修复场景**：
- 口语化：「这个怎么用啊」→「工具 使用方法 步骤 / 工具 使用教程 / 工具 操作示例」
- 短 query：「限流」→「API 限流策略 / 接口限流配置 / 限流规则说明」
- 多意图：「对比 X 和 Y 的区别以及使用场景」→ 分解为 2-3 条 sub-query
- 指代：「第几章？」（上文聊某条例）→「条例名 + 条款编号」

**高级配置**：
- 想用便宜模型做改写：「改写 Provider」+「改写模型」可独立指定（如 Qwen-Turbo / gpt-4o-mini）
- 想退回 v1.2.6 行为：取消勾选「查询改写 / 扩展」

**性能影响**：每条 user msg 多 1 次小模型调用（≈300-500 token，温度 0.1）+ 1-3 次额外 `hybridSearch` 检索；首问多 1-3 秒。

详见 [§5.7 查询理解与重写管线（v1.3.0）](#57-查询理解与重写管线v130)。

### Q22：明明文档里有正确答案，AI 却答错或说"没找到"怎么办？（v1.3.2）

**A**：可能是**正确答案被检索排序挤出 topK**——BM25 + RRF 融合把含 query 关键词多的长整章 chunk 排在前面，真正回答问题的子 chunk（如某几条具体条款）被压到 topK 外，LLM 拿到错的 chunk 就幻觉或说没找到。

v1.3.2 起，「设置 → 常规」默认勾选「**检索结果重排**」——检索召回 20 个候选片段，用 Chat Provider 小 LLM 按语义相关度重排，取 topK 喂主答 LLM。LLM 看 query+chunk 联合语义判断（而不是关键词堆砌），把真正回答问题的片段抬到前面。

**典型修复场景**：问"条例第二章第十三条前后关于备案事项的完整规定"——正确答案（第十九-二十二条）原本被 8 个整章总则 chunk 压到 rank 12，rerank 后 LLM 识别它才是"第十三条前后备案"的真匹配，抬到前 1-2，AI 完整列出 (一)~(六)。

**性能影响**：每问多 1 次小 LLM 调用（~几百 token，温度 0.1）；Agent 模式每次检索多 1 次。失败时（缺 key / LLM 抛错 / 返回非 JSON）自动回退 RRF 原顺序。

**想退回旧行为**：取消勾选「检索结果重排」。

详见 [§5.8 检索结果重排（v1.3.2）](#58-检索结果重排v132)。

### Q23：简单模式回答很慢怎么办？（v1.3.5）

**A**：v1.3.5 加了分步耗时日志定位慢在哪步。在主进程控制台看 `[chat] [timing]` 行，会打出 plan/embed/search/rerank/total 各多少 ms。

常见瓶颈：
- **rerank 慢（曾实测 33s）**：deepseek-v4-flash 等模型非流式响应慢（要等思考链+正文全生成完）。v1.3.5 已把 rerank 改流式 + 10s 超时兜底，实测降到 3.7s。若仍慢，可在「设置 → 常规」取消勾选「检索结果重排」
- **plan 慢（多轮 4s）**：query-rewriter LLM 调用，真思考时间流式省不了。可取消勾选「查询改写 / 扩展」退回单条原 query（但多轮指代消解/口语化扩展没了）
- **embed 慢（1-2s）**：embedding API 本身慢，单次调用优化空间小，可换更快的 embedding Provider

详见 [§5.9 检索性能优化（v1.3.5）](#59-检索性能优化v135)。
