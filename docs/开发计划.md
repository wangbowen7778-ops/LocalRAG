> 本计划基于 Vibe Coding 思路：文档先行 → 分阶段实施 → 增量验证。每完成一个阶段后更新 `开发进度.md`。

## 阶段四点五：智能切分 v1.2.1

### 目标
把「单一滑动窗口 char-based 切分」升级为「**按文件类型分发 + token-based 切分**」，让切片语义更完整、结构更可读。

### 任务清单
- [x] **`src/main/chunkers/`（新建）**：
  - `tokenizer.ts`：`gpt-tokenizer@3.4` cl100k_base（与 OpenAI text-embedding-3 同源）
  - `recursive.ts`（A+C）：LangChain 递归分隔符 `[\n\n → \n → 句号群 → 词 → 字符]`
  - `markdown.ts`（B+A+C）：`marked.lexer` 结构感知 + 标题面包屑 + 代码块/表格原子化
  - `pdf-layout.ts`（E+A+C）：pdfjs items 按 (页, y, x) 排版 + 跳页眉页脚（数字归一化）
  - `index.ts`：分发器
  - `gpt-tokenizer.d.ts`：TS moduleResolution=Node shim
- [x] **`document-processor.ts` 改造**：
  - 删 `splitChunks`；新增 `extractPdfTextItems`（带坐标）
  - `processAndIndexDoc` 按扩展名分发：`.pdf` 走 items + pdfItemsToText + recursive（失败 OCR 兜底），`.md` 走 markdownChunk，DOCX/TXT 走 extractText + recursive
- [x] **Settings**：`chunkSize` 500→800 tokens、`chunkOverlap` 50→100 tokens；UI 标签加 `(tokens)` 后缀
- [x] **`scripts/chunker-selftest.js`（新增）**：跑 3 种典型输入验证切分效果

### 交付物
- 纯文本：4 段切 2 chunks（每段 ~150-200 token）
- Markdown：4 级标题切 4 chunks，每个带 `【H1 > H2】` 面包屑
- 文本层 PDF：3 页 + 页眉页脚 → 正确去重页眉页脚 → 章节切分
- OCR PDF：降级到 A+C 切分（拿不到坐标）

### 已知边界
- PDF 不做分栏检测（双栏论文/期刊可能误读），如未来需要可加列检测
- gpt-tokenizer 字典 ~1.5MB，进程驻留

## 阶段五点六：对话上下文优化（v1.2.2 + v1.2.3）

### 目标
解决多轮对话 RAG 的两个核心痛点：
1. **指代 / 省略问句召回差**——"它是什么？" / "哪一章？" / "那关于 X 呢？" 类短问句 embed 后与上一轮实体向量偏离，命中率从 90% 跌到 30-50%
2. **长会话 history 越界**——session 超过 10 轮后，改写 LLM 自己也看不完 100 条历史；同时跨 session 的"我们之前聊过 X 吗"无法回答

### 任务清单

#### v1.2.2 查询改写

- [x] **`src/main/api-client.ts::rewriteQuery(provider, key, model, messages, currentMsgId, query, sessionId)`（~150 行）**：
  - **跳过判定**：`ANAPHORIC_RE = /[它他她这那]|刚才|那个/`；query 长度 ≥ 6 且不匹配 → 直接返回原 query（0 LLM 调用）
  - **改写 prompt**（`REWRITE_PROMPT`）：给 LLM 看压缩后的最近 8 条历史 + 当前 query，输出**改写后的一行 query**（无解释）
  - **进程内缓存**：`rewriteCache: Map<sessionId, Map<key, string>>`；key = `(lastUserContent + '|' + currentQuery)`；命中后 0 LLM 调用
  - **失败回退**：Provider 4xx/5xx/网络超时 → `console.warn` + 返回原 query，不阻塞主流程
  - **导出** `clearRewriteCache()`：设置变更时主动清空
- [x] **`src/main/document-processor.ts::resolveRewriterProvider(settings)`**——镜像 `resolveEmbeddingProvider`：
  - `rewriterProviderId` 非空 → 用其 Provider / `rewriterModel`
  - 空 → 复用 `defaultProviderId` / `defaultModel`
- [x] **`src/main/ipc-handlers.ts::applyQueryRewrite(sessionId, userMsgId, chatApiKey, settings, userContent)`**：
  - `enableQueryRewrite === false` → 直接返回原 userContent
  - 调 `rewriteQuery`；失败/异常 → 静默回退
- [x] **simple 模式**：`runSimpleChat` 用 `effectiveQuery` 替换原 `payload.content`（embed + hybridSearch + prompt 全部用 effectiveQuery）
- [x] **agent 模式**：`AgentInput.effectiveUserContent?: string` 透传；`agent.ts` 内部 `effectiveUserContent ?? userContent`
- [x] **Settings 增 3 字段**：`enableQueryRewrite?: boolean`（默认 `true`）/ `rewriterProviderId?: string` / `rewriterModel?: string`
- [x] **SettingsDialog**：常规 tab 加 3 行 UI（checkbox + 改写 Provider 下拉 + 改写模型输入框）

#### v1.2.3 长会话上下文

- [x] **`src/main/api-client.ts::buildRewriteHistory(messages, currentMsgId)`**：
  - **4 步压缩**：过滤 tool/系统消息 → 必带 firstUser 锚定 → 取最近 10 条 → 倒序按 2500 字预算填
  - **assistant 截断**：单条 > 500 字时截到 300 字 + `…`（保留前 300 字核心）
  - **`REWRITE_HISTORY` 常量**：`MAX_MESSAGES=10` / `ASSISTANT_TRUNCATE_THRESHOLD=500` / `ASSISTANT_TRUNCATE_LENGTH=300` / `MAX_CHARS=2500`
- [x] **`src/main/api-client.ts::summarizeConversation(messages, provider, key, model)`**：
  - **prompt 模板**（`SUMMARIZE_PROMPT`）：要求 LLM 输出 `summary` 一段 + `keyTopics` 列表 + `keyEntities` 列表
  - **解析**：尝试 JSON.parse，失败回退到"全文当 summary、keyTopics/Entities 空"
- [x] **`src/main/storage.ts` 新增 `session_summaries` 表**：
  - 列：`id` / `session_id` / `start_msg_id` / `end_msg_id` / `summary` / `key_topics` / `key_entities` / `created_at`
  - 索引：`(session_id, created_at DESC)`
  - **5 个 CRUD 函数**：`addSessionSummary` / `getLatestSessionSummary` / `listSessionSummaries` / `searchSessionSummaries`（跨 session SQL LIKE）/ `deleteSessionSummaries`
  - `deleteSession` 级联调 `deleteSessionSummaries`
- [x] **`src/main/ipc-handlers.ts::maybeSummarizeSession(...)`（fire-and-forget）**：
  - 触发条件：自上次摘要以来 user turn 数 ≥ `summaryTriggerTurns`（默认 20）
  - **关键**：`void maybeSummarizeSession(...)`——不 `await`，不阻塞 chat 主流程
  - 失败 `console.warn` 跳过；下次 user 消息再试
- [x] **历史摘要召回注入**：
  - `runSimpleChat`：每次发问调 `searchSessionSummaries(payload.content, 2)` 命中 top 2 → 拼 `summaryBlock` 加到 user prompt 顶部
  - `agent.ts`：fallback + 流式 final 都注入 `summaryBlock`
- [x] **Settings 增 1 字段**：`summaryTriggerTurns?: number`（默认 20；0 = 关闭）
- [x] **SettingsDialog**：周期摘要阈值数字输入框（0-200，默认 20）
- [x] **`scripts/rewrite-selftest.js`（新增）**：
  - **Part A** 11 个本地跳过判定 case（无 LLM 调用，0 凭据）
  - **Part C** 5 个 `buildRewriteHistory` case（无 LLM 调用，验证压缩逻辑）
  - **Part B** 4 个端到端 LLM case（设 `REWRITER_API_KEY` 才跑，含缓存命中验证）

### 交付物

- 用户发"哪一章？" / "它是什么？" / "刚才那个文件呢？" 类追问时，**自动改写**为自包含 query 再检索，召回率从 30-50% 回升到 80-90%
- 长 session（> 10 轮）改写 LLM 仍只看到 ≤ 2500 字 token 预算的历史
- 跨 session 的"我们之前聊过 X 吗"问题，自动从 `session_summaries` 命中 top 2 历史摘要注入到 LLM 上下文
- 周期摘要**不阻塞** chat（fire-and-forget），用户感知不到
- 默认开启；用户可在「设置 → 常规」关掉（设为 `false` / 0）

### 已知边界

- 摘要是**异步**生成——刚结束的 turn 不会立刻被检索到
- 改写 + 摘要复用同一 Provider/模型；token 消耗约 1-2K/次摘要
- `summaryTriggerTurns = 0` 关闭摘要但**保留改写**（适合不想异步调 LLM 的用户）
- v1.2.2 与 v1.2.3 不依赖 Agent 模式——简单模式同样享受改写 + 摘要收益
- `ANAPHORIC_RE` 故意只列 5 字 + 2 短语（`它他她这那` + `刚才/那个`），假阳率最低但召回不完美

> **v1.2.4 重构**：v1.2.2 改写 / v1.2.3 `buildRewriteHistory` / v1.2.3 `ANAPHORIC_RE` / `rewriteCache` 在 v1.2.4 **全部删除**。新的「阶段五点七」用 `buildHistory` 智能 context 截断 + read_chunk 工具流替代上述逻辑——LLM 看到全 history 自然消解指代，不需要额外改写 LLM 调用。

## 阶段五点七：智能 context 截断 + read_chunk 工具（v1.2.4）

### 目标
清理 v1.2.2 query rewriting 过度设计 + 解决"chunk 全文塞 LLM 太长"问题。两件套：
1. **智能 context 截断**——`buildHistory` 按模型 context window 智能放 history，能塞下就全塞
2. **read_chunk 工具**——检索后只发"索引 + preview"给 LLM，LLM 按需 `read_chunk(chunk_id)` 拉完整内容

## 阶段五点八：检索 query 消解（v1.2.5 → v1.2.6）

v1.2.4 把"指代 / 实体补全"完全寄托给 LLM（"LLM 看到全 history 时消解是无成本的"），但**只对 LLM 有效，对检索无效**——`embedText` + `hybridSearch` 发生在 LLM 看到 history 之前，拿的是裸 query，embedding 和 BM25 不知道历史。本阶段分两版解决：

### v1.2.5（已重构）—— 检索 query 消解首版

#### 目标
新建 `src/main/query-resolver.ts`，在 `runSimpleChat` 检索前先把 user query 改写为 self-contained 检索 query，结果**只用于 `embedText` + `hybridSearch`**，**不进 LLM context**（LLM 反正自己看 history 也能消解）。

#### 任务清单
- [x] **新建 `src/main/query-resolver.ts`**——三件套：
  - `stripQuestionTail(query)`：cheap regex 剥除"这是哪个文件的内容？" / "这是哪部法规？" / "出自哪里？"等问句尾巴；前缀分隔符只用 `[；;\s]*` 不含 `。`（避免误吞句末标点）

- [x] **Agent 模式不动**：LLM 自己调 `search_kb` 输出 sub_query，指代自然消解
- [x] **`src/shared/constants.ts` + `package.json`**：version 1.2.4 → 1.2.5

### v1.2.6（已被 v1.2.7 替代）—— 删 regex 门控 + 补 agent sub_query 自包含

#### 触发 bug
用户实测：上文聊"《北京市殡葬管理条例》第十四条的内容是什么" → 追问"第几章？"：
- **简单模式**返回毫不相关的文档条款（中医条例 / 动物防疫条例 / 国际科创中心条例）
- **Agent 模式**（已开启）同样返回毫不相关的文档条款

#### 根因
- **简单模式**：v1.2.5 `isAnaphoric` regex 漏判"第几章？"（"几"不在表里）→ `passthrough` "第几章？" → embedding/BM25 召回全 KB 噪声
- **Agent 模式**：`AGENT_SYSTEM_PROMPT` 和 `AGENT_TOOLS.sub_query.description` 没显式告诉 LLM "sub_query 必须自包含"——LLM 直译"第几章？"给 `search_kb`

#### 设计反思
- **分类问题天然不该用 regex**——"用 regex 检测指代再决定要不要调 LLM 改写"是分类任务，开放表达永远盖不全（用户实测："第几章？"的"几"不在表里 / "原文呢" / "适用范围" / "处罚标准呢" / "对比一下" / "举个例子" / "它的限流策略" / "为什么" / "详细说说" 等大量真实指代都漏）
- **检索系统是 stateless 的**——`embedText` + `hybridSearch` 发生在 LLM 看到 history 之前，**LLM 端能消解 ≠ 检索端能消解**
- **always-LLM vs 选择性 LLM**——v1.2.5 的"先 regex 判断再决定调不调"看似省 LLM 调用，但误判率太高，漏的 case 后续会被用户重复触发；always-LLM 在 multi-turn 会话里总成本更低

#### 任务清单
- [x] **`query-resolver.ts` 重构**（~230 行 → ~190 行）：
  - **删除** `TAIL_FILE_QUESTION_PATTERNS` / `stripQuestionTail()` / `ANAPHORIC_STARTERS` / `isAnaphoric()` 四件套
  - **简化** `steps` 类型：5 元 → 4 元（删 `'tail-strip'`）
  - **主流程三步走**：cacheKey 命中 → 首轮 passthrough → 有 history 总是 `llm-call`
  - **`condenseWithLlm` anchor 扩到最近 6 条 user/assistant**（≈3 轮）——v1.2.5 是"末条 user msg"，LLM 看不到前一轮 assistant 答案里的实体名
  - **Prompt 重写**：多规则 system prompt（3 条指令：已自包含原样返回 / 含指代用 history 实体名补全 / 只输出 query 文本不要解释）+ user 端 `【对话历史】\n...\n【本轮问题】\n...` 模板
  - **回退链不变**：缺 key / LLM 抛错 / 返回空 / 返回同 query → fallback 原文
  - **清洗逻辑保留**：去首尾引号 + 截第一行
- [x] **`agent.ts` AGENT_SYSTEM_PROMPT 重写**：
  - 顶部加 `⚠ 调 search_kb 之前：sub_query 必须自包含` 警示段
  - 加 3 个正反例：上文聊《北京市殡葬管理条例》第十四条 → "第几章？" → sub_query="北京市殡葬管理条例 第十四条"；上文聊 OpenAI API → "它的限流策略呢" → sub_query="OpenAI API 限流策略"；自包含 "5G 和 4G 的区别" → 原样使用

- [x] **`src/shared/constants.ts` + `package.json`**：version 1.2.5 → 1.2.6

## 阶段五点十：查询理解与重写管线（v1.3.0）

## 阶段五点十一：query-rewriter 入口加 stripNoise 预处理（v1.3.1）

### 背景

## 阶段五点十二：检索后 LLM rerank（v1.3.2）

### 背景

v1.2.8/v1.2.9 调了一轮 BM25/RRF 参数（topK 5→8、fetchK=max(50,10×topK)、RRF_K 60→30、b 0.75→0.5）但没根治「正确答案被排到 topK 外」。用户实测复现「北京历史文化名城保护条例 第二章第十三条前后备案事项」：BM25 把正确答案（chunk 7 含第十九-二十二条）排到 rank 12，8 个整章 chunk 的 BM25 分数挤在 10% 区间内（29.97/27.04/26.81/...），区分度极低；RRF 融合后答案落到 rank 6 边缘，topK 切掉，LLM 拿到整章总则 chunk 幻觉出"第四章只有第三十四条"。

根因：BM25 中文 unigram 分词让条例名前缀（每章节 chunk 都以「北京历史文化名城保护条例 第N章」开头）稀释 IDF，8 个整章 chunk tf 命中 query 关键词次数多 → BM25 分高；length norm 力度不够压不住长 chunk。继续调参边际递减——根因是 BM25 对中文长结构化文档区分度本身不够，不是参数没调对。

### 目标

用 LLM 语义重排（CLAUDE.md v1.2.8 已预留为"终极方案"）：召回扩大到 20 候选 → 小 LLM 看 query+chunk 联合语义重排 → 取 topK。LLM 能识别「第十九-二十二条备案」才是「第十三条前后备案」的真匹配，把答案从 rank 6+ 抬到前 1-2。

### 任务清单

- [x] **`src/main/reranker.ts`（新建 ~150 行）—— `rerankHits(query, hits, settings)`**：

### 关键设计取舍

- **不改 vector-store 检索签名**——扩召回靠调用方传大 topK
- **不替换 score**——rerank 只重排，RRF norm score 保留，threshold/citation 零侵入

- rerank 候选上限 20——更大的候选池会让 rerank LLM prompt 变长、变慢；20 是经验值
- 按条切片（根治 BM25 tf 稀释的另一条路）——留 v1.4.0+ 评估

## 阶段五点十三：rerank 启用时直接发全文（v1.3.3）

### 背景

v1.3.2 rerank 把正确 chunk 精确搜到了，但用户实测「第二章第十三条前后备案事项」仍答截断——AI 说"参考资料中该条款内容被截断…当前环境暂不支持拉取完整文档"，只答出 (一) 就停。citation 列表里有完整全文（第十九-二十二条），LLM 却说截断。

根因：简单/agent 模式都走 read_chunk preview 流（v1.2.4）——chunk 全文 > 200 字时只发前 200 字 preview + `[TRUNCATED]` 标记，依赖 LLM 主动调 `read_chunk` 拿全文。v1.2.7 加硬规则"列举/条款型必须先 read_chunk"，但弱模型不遵守：`runSimpleChatWithTools` line 440 兜底「LLM 没调 tool（`toolCalls.length===0`）就直接用 preview 答」→ 截断错误答案。rerank 搜到了却卡在 read_chunk 这步没用上。

### 目标

rerank 启用时跳过 read_chunk preview 流，直接发 topK 全文。rerank 已精确挑出语义最相关 chunk，全文成本可接受，且不再依赖 LLM 主动调工具。

### 任务清单

- [x] **`src/main/ipc-handlers.ts::runSimpleChat`**——`useToolFlow` 加 `&& !enableRerank`：rerank 开 → 走 `runSimpleChatLegacy` 全文路径；rerank 关 → 保持 read_chunk preview 流
- [x] **`src/main/agent.ts::runAgent` search_kb 响应段**——rerank 开时发 `filtered` 全文（`[#N filename]\n${h.text}`，不调 `formatChunkPreview`）；关时保持 preview 流；chunkMap 仍建（read_chunk 兜底）
- [x] **无新增 Settings 字段**——绑定 `enableRerank`（rerank 开=全文，rerank 关=read_chunk）

### 关键设计取舍

- **rerank 已精确挑出 topK**——全文成本可接受（topK=8 约 6.4K token），不再依赖 LLM 主动调工具
- **rerank 关闭时保持 read_chunk 流**——无 rerank 时 chunk 质量参差，LLM 选择性读省 token 有价值
- **chunkMap 仍建 + read_chunk 工具仍注册**——兜底，不删避免大改
- **不改 preview 长度 / 不强制 tool_choice**——治本（发全文）比治标（加长 preview / 强制调工具）可靠

### 已知边界

- rerank 开 + topK 大（如 20）时全文 token 较多——但 rerank 后 topK 默认 8，可接受；用户嫌慢可关 rerank 退回 read_chunk 流
- agent 模式多次 search_kb 累积全文——maxIterations=4 × topK=5 最多 20 个 chunk 全文 ≈ 16K token，可接受
