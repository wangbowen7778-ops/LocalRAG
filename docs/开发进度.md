### v1.2.6（2026-06-12）— 检索 query 消解去 regex 门控 + agent sub_query 自包含 prompt
- **问题**：
  1. v1.2.5 的 `isAnaphoric` regex 是 cheap cost gate，但**分类问题天然不该用 regex**——用户实测："第几章？"（"几"不在表里）/ "原文呢"（"原文"不在表里）/ "适用范围" / "处罚标准呢" / "对比一下" / "举个例子" / "它的限流策略" / "为什么" / "详细说说" 等等大量真实指代都漏判，漏了就被 `passthrough` 喂检索，embedding/BM25 拿裸 query 召回必错
  2. Agent 模式即使 v1.2.5 不动（依赖 LLM 自调 `search_kb` 输出 sub_query），实测仍失败：用户开 agent 模式问"第几章？"返回毫不相关的文档——`AGENT_SYSTEM_PROMPT` 和 `AGENT_TOOLS.sub_query.description` 没明确告诉 LLM "sub_query 必须自包含"，LLM 直译了"第几章？"三个字给检索
- **根因**：
  1. 检索系统（向量库 + BM25）是 stateless 的——`embedText` + `hybridSearch` 发生在 LLM 看到 history 之前，拿的是裸 query；**LLM 端能消解 ≠ 检索端能消解**

### v1.3.5（2026-06-25）— 检索性能优化（耗时日志 + rerank/plan 改流式 + 超时兜底）
- **问题**：用户实测简单模式慢，需要定位慢在哪步
- **诊断**：加 分步耗时日志（`ipc-handlers.ts::runSimpleChat`）——`timing` 对象记录 plan/embed/search/rerank 各步 ms，检索段结束打 `[chat] [timing] session=... plan=Xms embed=Xms search=Xms rerank=Xms hits=N`，主答完成打 `total=Xms`。用户跑出数据：**rerank 33 秒**是主凶
- **根因**：deepseek-v4-flash 非流式 `chatCompletion`（`stream:false`）要等思考链+正文全生成完才一次性返回，10-33s 超时。非流式时服务端长时间不返回任何字节，容易触发超时
- **修复（三件套）**：
  - **(1) rerank/plan 改流式**——`reranker.ts::rerankHits` 和 `query-rewriter.ts::planWithLlm` 的 LLM 调用从 `chatCompletion`（非流式）改成 `chatStream`（流式），onDelta 传空（不流式给 UI，只要最终 content）。流式让服务端不用缓冲整个思考链，正文一出就能收，思考链 reasoning_content 边来边丢。**实测 rerank 33s→3.7s**；plan 4s 没降（4s 是真思考时间，流式省不了，但至少不超时）
  - **(2) rerank 10s 超时兜底**（`reranker.ts` `RERANK_TIMEOUT_MS=10_000`）——`Promise.race` 包 chatStream，超时回退 RRF 原顺序（`return hits`），最差 10s 而不是 33s
  - **(3) reranker 诊断日志**——`[reranker] provider=... model=... candidates=N prompt=N字 response=N字 llm=Nms finish=...`，定位 rerank 慢的根因
- **关键认知**：流式加速 = 省掉服务端缓冲 + 避免思考链憋超时，**不是省"生成时间"**。rerank 33s→3.7s 立竿见影是因为之前 33s 大部分是非流式缓冲/超时浪费（不是真在思考 33s）；plan 4s 是真思考，流式省不了

### v1.2.1（2026-06-07）— 按文件类型分发的智能切分（chunkSize 改 token 单位）
- **问题**：
  1. 老的 `splitChunks` 按 500 字符硬切，PDF 没段落结构时（pdfjs 每页只插 `\n` 不插 `\n\n`，多页之间才 `\n\n`）基本是按 char 横切，句子常被腰斩
